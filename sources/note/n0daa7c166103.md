# プロンプトの技より、先に稽古法がいる

## ― AIユーザーに必要なのは、プロンプトエンジニアリングよりコミュニケーションの責任だ

AIを使っていると、だんだん増えていくものがある。  
プロンプトの工夫だ。  
こう書けば精度が上がる。  
この順番で指示すると安定する。  
この一文を入れると暴走しにくい。  
最近では、再利用可能な形で指示や手順をまとめるやり方も広がっている。OpenAI は prompt engineering のベストプラクティスを案内し、Anthropic や GitHub も SKILL.md を中核にした skills を、必要時に読み込む再利用可能な仕組みとして提供している。

私は、こうした工夫自体を否定したいわけではない。  
実際、効くこともある。  
表層の出力は整うし、暴れやすい挙動をある程度抑えることもできる。  
だから、不要だとは思わない。

ただ、使っていてずっと気になっていることがある。  
それは、こうした対応が積み上がるほど、どこで何が起きているのかが、かえって見えにくくなることだ。

この違和感を、私は武術に少し似ていると思っている。  
技をたくさん覚えても、それだけでは使えない。  
いつ、どこで、どういう状況で、その技を出すのか。  
何を見て、何を捨てて、その技を選ぶのか。  
そこが分からなければ、技はただのコレクションになる。  
開祖や達人は使えるかもしれない。  
だが、その技だけを他人に渡しても、渡された側は、どこで使えばいいのか分からないまま終わることがある。

プロンプトエンジニアリングにも、これに近い危うさがある。  
成功した局所解は、技として保存しやすい。  
このテンプレ、この指示、この skill。  
だが、それがどの失敗に対する応答として生まれたのか、どの文脈で効くのか、何を防ぐためのものなのかが失われると、技は呪文集になる。  
少し整うことはある。  
だが、**つぎはぎ的な対応ほど、結果はガチャ化しやすい。**

私はこの問題を、ベンダー視点で見ているわけではない。  
モデル内部をどう改修するか、学習目標をどう変えるか、そんな話をしたいのではない。  
私は一ユーザーとして、現状のAIを使うとしたら、何を根本に置くべきかを考えている。  
その前提では、プロンプトエンジニアリングや SKILL.md は、根本対応ではなく、あくまで局所技術に見える。

ここで言いたいのは、技法が悪いということではない。  
問題は、**技法が先に来て、何を失敗と呼ぶのか、どのレイヤーでずれが起きているのか、誰がどの責任を持つのかが曖昧なままになること**だ。  
これは一般論ですが、技法は問題を解くこともあるが、問題の見え方そのものを整えるわけではない。  
その意味で、ユーザー側に本当に必要なのは、長いプロンプトや大量のスキルではなく、**AIとのコミュニケーションをどう見るかの上位原理**のほうだと思う。

私は、その上位原理を少なくとも四つに分けて考えている。

一つ目は、**人間側が、AIに入力する言葉の意味に責任を持つこと**である。  
ここで言う責任は、完璧な入力を書けという意味ではない。  
そうではなく、いま自分が何を聞いているのか、どのレイヤーで話しているのか、その言葉をどういう意味で使っているのかを、自分のものとして引き受けることだ。  
AIに曖昧な言葉を投げておいて、あとは全部AIがうまく読め、では済まない。  
入力の意味に対して、人間も当事者である。  
ここが出発点になる。

二つ目は、**AIが人間の言葉をどう解釈したのかに敏感になること**である。  
AIの問題は、結論を間違えることだけではない。  
もっと手前で、言葉を何として読んだのかがずれる。  
比較の話を一般論として読む。  
文脈限定の話を絶対命題に直す。  
体感に基づく観測を、普遍命題として処理する。  
このずれが起きたまま出力だけ整っていると、会話は一見成立しているようで、実はかなりずれている。  
だから本当に見なければならないのは、AIが何を答えたかより前に、**何として読んだか**である。

三つ目は、**AIが出してきた文章について、結論よりも、どういうステップで検討したのかを注意深く観察すること**である。  
ただし、ここで言うステップとは、AIが自己申告するもっともらしい思考説明をそのまま信じることではない。  
見るべきなのは、出力の中に現れている読解の痕跡だ。  
元の文より強くなっていないか。  
元の文より広くなっていないか。  
留保が消えていないか。  
本文と補記、事実と解釈、比較と一般論の境界が混ざっていないか。  
結論だけを見ていると、こうしたずれは見えにくい。  
だが、むしろ危ないのはその途中である。

四つ目は、**AIが出してきた結論を多角的に検証すること**である。  
ただし、ここでも危ないのは、結論だけを正誤判定して終わることだ。  
検証すべきなのは、結論の妥当性だけではない。  
そこに至るまでに、何が削られ、何が足され、何が勝手に一般化されたのかも含めて見る必要がある。  
もっともらしい結論は、それだけで危うい。  
気持ちよく整理された結論ほど、途中の損失が見えにくくなるからだ。

この四つは、ばらばらの注意事項ではない。  
一つ目の「責任」が土台になって、二つ目から四つ目へつながる。  
自分の入力した言葉の意味を、自分のものとして引き受ける。  
その前提があってはじめて、AIが何として読んだかを見ようという話になる。  
そして、その読みが出力にどう現れたかを観察し、その結果を検証する。  
つまりこれは、**入力―解釈―観察―検証**の連鎖であり、コミュニケーション回路全体の責任分担の話である。

私は、ここがプロンプトエンジニアリングと決定的に違うと思っている。  
プロンプトエンジニアリングは、主にどう言わせるかを扱う。  
SKILL.md は、その技を再利用可能な形でまとめる。  
どちらも有効ではある。  
だが、それだけでは、何を入力責任とし、AIの読みをどう観察し、出力をどう検証するかという上位の枠組みは生まれない。  
だから、技だけが増えやすい。  
そして技だけが増えるほど、全体としてどこで何が起きているのかが見えにくくなる。Anthropic は skills を relevant なときに読み込む仕組みとして説明し、GitHub も skills を instructions・scripts・resources の束として位置づけているが、それ自体が「読み違えをどう検知し、どう責任分担するか」まで保証するわけではない。

私が言いたいのは、プロンプトエンジニアリングをやめろということではない。  
そうではなく、順番の問題だ。  
先に必要なのは技ではない。  
**どこで何が壊れ、誰が何を引き受け、どのように検証するのかを見る稽古法**である。  
その上で初めて、技は意味を持つ。  
順番が逆だと、技は増えるが、使いどころは分からないままになる。

AIを使うとは、便利な文章生成器を操縦することだけではない。  
人間が入力した言葉が、AIによって何として読まれ、どう再構成され、どの結論として返ってくるかを扱うことでもある。  
だからユーザー側に必要なのは、技の収集よりも先に、**コミュニケーション回路に対する責任感覚**だと思う。

私はそこを、プロンプトエンジニアリングよりもう一段根本に近いものとして見ている。  
技法の問題ではなく、稽古法の問題。  
局所解のコレクションではなく、何を見るかの問題。  
そこを間違えると、AIはますます便利になるかもしれない。  
だが、人間がどこで何を見失っているのかは、ますます分からなくなる。

## 補記

### 1. 研究名

OpenAI の prompt engineering ガイド

### 2. 研究者

OpenAI

### 3. 本文との共通点

OpenAI は、明確で具体的な指示や、段階的な改善によって出力品質を上げる prompt engineering の実践を案内している。本文が、プロンプトの工夫それ自体には効果があると認めている点は、この前提と重なる。

### 4. 本文との差分

OpenAI のガイドは主に「どう指示を書くと、より望ましい出力が得られるか」を扱っている。本文はそこからさらに、**良い指示を書くこと**と**何を失敗と見て、どこでずれを観察し、どう責任分担するか**は別問題だと押し広げている。つまり本文は、prompt engineering を上位原理の下に置くべき局所技術として見ている。

### 1. 研究名

Claude Code の skills / SKILL.md

### 2. 研究者

Anthropic

### 3. 本文との共通点

Anthropic は Claude Code docs で、SKILL.md を用いた skills を、必要時に読み込まれる再利用可能な指示・補助リソースの束として説明している。本文が、skills を「再利用可能な技」として扱っている点は、この設計と重なる。

### 4. 本文との差分

Anthropic の skills は、再利用可能なワークフローや手順を整えるための仕組みであって、AIが人間の言葉を何として読んだか、どこで読み違えたか、誰がどの責任を持つかを主題にはしていない。本文はそこからさらに、**skills は局所技術として有効でも、それを位置づける稽古法がなければ全体は見えにくくなる**という方向へ押し広げている。

### 1. 研究名

GitHub Copilot の agent skills

### 2. 研究者

GitHub

### 3. 本文との共通点

GitHub は Copilot の agent skills を、SKILL.md と補助リソースからなる再利用可能な能力として整理している。本文が、skills を技のパッケージ化として見ている点は、この設計と接続する。

### 4. 本文との差分

GitHub の skills は、特定タスクで必要な instructions・scripts・resources をまとめる実装上の枠組みであり、ユーザーが入力責任・読解観察・出力検証をどう持つべきかまでは扱わない。本文はそこからさらに、**skills の利用を支える上位のコミュニケーション原理がなければ、技の収集はハッチポッチパッチ化しやすい**という方向へ押し広げている。

### 1. 研究名

“The Preference for Self-Correction in the Organization of Repair in Conversation”

### 2. 研究者

Emanuel A. Schegloff / Gail Jefferson / Harvey Sacks

### 3. 本文との共通点

会話分析における repair 論は、会話の中で生じる trouble をどのように修復するかを中心問題として扱う。本文が、AIとのやり取りでは結論よりも「どこで何をどう読んだか」を観察し、ずれが起きたらそこを開いて立て直すことが大事だとしている点は、この視点と重なる。

### 4. 本文との差分

既存の repair 論は主に人間同士の会話を対象としており、プロンプトエンジニアリングや skills の運用を直接論じてはいない。本文はそこからさらに、**AIユーザー側にも、repair を支える上位原理を持つ必要がある**という方向へ押し広げている。つまり、会話の修復を、AI利用の稽古法そのものへ接続している。
