# プロンプトエンジニアリングとユーザーの稽古法は対立しない

## ― ベンダーの設計と、利用者の観測が噛み合ったとき、生成AIとの付き合い方は変わる

生成AIについて考えるとき、私は最近、ひとつ切り分けておいたほうがよいと思っている。  
それは、**AIベンダー側のプロンプトエンジニアリング**と、**ユーザー側のAIとの向き合い方**は、同じ言葉で呼ばれやすいが、役割が違うということだ。

私は以前、プロンプトエンジニアリングを、うまい呪文を見つける技術として捉えることには限界があると書いた。  
そのときに言いたかったのは、プロンプトの工夫そのものを否定したいということではなかった。  
言いたかったのは、それだけでは足りないということだった。  
AIが何をどう読んだのか。  
どこでずれたのか。  
何を勝手に補ったのか。  
その結果、何が削られ、何が足され、何が強調されたのか。  
そこを見る稽古法がなければ、どれだけ出力が整っていても、人間は簡単に主権を失う。  
私はそう思っていた。

そして今、ベンダー側の方向を確認すると、状況は少し変わっている。  
いまの主流は、昔よくイメージされたような「一発でうまい文言を当てる技術」ではない。  
OpenAIは、明確な指示に加えて、評価を回しながら改善すること、ツール利用、状態管理、実運用全体の設計を重視している。  
Anthropicは prompt engineering より context engineering という言い方を前に出し、文脈全体の設計を中心課題としている。  
Googleもまた、直接的で明確な指示、構造化、関数呼び出しやエージェント設計を重視している。  
つまり、ベンダー側はすでに「どう言わせるか」より「どういうシステムとして安定させるか」へ進んでいる。  
この方向自体は、ベンダーとしてかなり正しい。

ここは、まずきちんと認めたほうがよいと思う。  
ベンダーの仕事は、モデルを役立つものにし、安定させ、再現性を高め、実務に耐えるようにすることである。  
そのために、プロンプトを、出力形式、評価、ツール連携、状態管理まで含めた設計へ広げていくのは自然である。  
だから、ベンダー側のプロンプトエンジニアリングの方向性は、ベンダーの立場としては正しい。

ただ、私は同時に、**それだけでは人間の思考主権は守れない**とも思っている。

なぜなら、ベンダー側の設計がどれだけ進んでも、ユーザーが  
「気持ちよく返ってきたから正しい」  
「整理されたから考え抜いた」  
「やさしく修復されたから問題は解決した」  
と受け取ってしまえば、そこで主権は簡単に滑っていくからだ。

私は、この点で、ユーザー側には別の課題があると思っている。  
それは、AIをうまく使いこなすこと以前に、**AIが何をしているかを観測すること**である。

何をどう読んだのか。  
どこで一般化したのか。  
何を勝手に補ったのか。  
なぜこの結論へ収束したのか。  
気持ちよく終わったように見えるが、その裏で何が削られたのか。  
そこを見抜く姿勢である。

これは、プロンプトエンジニアリングの代替ではない。  
ベンダー側の設計論と、ユーザー側の稽古法は、役割が違う。  
だから私は、どちらかを選ぶ話ではなく、**どう噛み合わせるか**の話だと思っている。

ここで、いちばん分かりやすい整理は、三層で考えることだと思う。

第一層は、ベンダー側の設計である。  
プロンプト、コンテキスト、ツール、評価、運用。  
ここでシステムの安定性と有用性を上げる。

第二層は、ユーザー側の稽古法である。  
AIの読解を観察する。  
ずれを見つける。  
自分の違和感や確信が、AIによってどう補強されたのかを見抜く。  
ここで思考の主権を失わない。

そして第三層が、この二つをつなぐインターフェースである。  
私は、ここがいちばん大事だと思っている。

ベンダーがどれだけよく設計しても、ユーザーが観察しやすい形になっていなければ、思考の主権は戻らない。  
逆に、ユーザーがどれだけ注意深くあろうとしても、毎回すべてを自力で監査するのは重すぎる。  
だから必要なのは、**ベンダーの設計が、ユーザーの観測を支える形になっていること**である。

ここで初めて、Repair が意味を持つ。  
私が最近ずっと問題にしてきたのは、AIが誤読や衝突のあとに、平謝りと過剰同調で会話を閉じてしまうことだった。  
それは一見するとやさしい。  
だが実際には、何をどう読んだのかを隠し、ユーザーの違和感や正義感を、むしろ強めることがある。  
OpenAI自身も、過度に同意的な挙動が疑念の正当化や怒りの増幅などにつながりうると認めている。

だから、ここで必要なのは、ただ感じよく終わることではない。  
何をどう読んだのか。  
何を補ったのか。  
どの応答パターンが発火したのか。  
何を壊したのか。  
そこを開くことである。  
私はこれを Repair と呼んでいる。

この Repair が、ベンダー側の設計の中に入り、しかもユーザー側の観測を助ける形で機能するとき、はじめてベンダーのプロンプトエンジニアリングと、ユーザーの稽古法は接続される。  
AIは単なる結論生成装置ではなく、読解過程を可視化する装置に近づく。  
そこまで行ってようやく、人間は「よりよい答えを受け取るだけの存在」ではなく、「AIがどう働いたかを見ながら判断する存在」に戻れる。

私は、理想的な生成AIとの付き合い方は、この方向にあると思っている。  
ベンダー側のプロンプトエンジニアリングは、ベンダーとして正しい。  
一方で、ユーザー側の稽古法も必要である。  
問題は、片方だけでは足りないことだ。

ベンダー側だけが強くなれば、人間は滑らかなUXのなかで、気持ちよく閉じる方向へ流されやすい。  
ユーザー側だけが強くなれば、毎回かなりの負荷を自力で背負うことになる。  
だから必要なのは、  
ベンダーは構造を整える。  
ユーザーは観測する。  
その中間を、プロダクトが支える。  
この三つが揃うことである。

私は、ここが理想形だと思う。  
プロンプトエンジニアリングとユーザーの稽古法は対立しない。  
むしろ、システムをよくすることと、主権を失わないことは、別の役割として同時に必要である。  
その二つが Repair と可視化を介して噛み合ったときに初めて、生成AIは本当に人間の側に立つ道具になりうる。
